# Network protocol

The custom WebSocket protocol between the headless server and every station (FT-NET-004, D70). Code: `net/net_protocol.gd` (message set, control codec), `net/snapshot_builder.gd` and `net/sections/` (snapshot codec), `net/net_chunker.gd` (chunks and bundles). The threads and seams are in `net/README.md`.

Protocol version: `NetProtocol.PROTOCOL_VERSION` = 8. Bump it on any incompatible change. Version 8 (M4, #11) adds ShipAdd, ShipTeam, SessionMode and Relaunch (types 41 to 44) and the `fleet`, `takeover`, `handover`, `scoreboard`, `eliminated`, `relaunch_votes`, `relaunched` and `session_over` events and the Welcome `tls` flag, under "Multi-ship sessions and PvP"; a version 7 peer would drop the new types. Version 7 (M3, #10) adds the HostPause message (type 40), the COMMS and SITES snapshot sections (kinds 15 and 16), the HELM fields `target_site`, `jump_left`, `jump_target` and `docked_site`, the FEEDS `flags` rows, the `debrief` and `lanes` events and the `host` flag of the `pause` and `resume` events, and removes the `sites` event (the SITES section replaces it); the station commands for the jump drive, docking, site targets, Comms and the Shakedown are listed under "Station commands added in M3". Version 6 (M3, #10, D229, D230) removes the space id from positions: the KIN section loses its u16 site (25 B), the Mark, Ping, route, zone and inbox messages carry `x`, `y`, `z` only, a `site` ping names its named site in `id`, the SCIENCE block loses `mark_site`, and the default period is 400 km; a version 5 peer would misread them. Version 5 (M2, #9) adds types 23 to 27 and 29 to 30 (Toggles, Chip, MainView, MarkSend, MarkAccept, ClientStats, Share), the SCIENCE, RELAY, CAPTAIN and CHIPS sections and the twelve new joint views; their rows are added below as each lands. Version 4 added Alert, Mark, Ping and RunAgain (types 19 to 22), the `alert`, `marks`, `ping`, `run_over` and `run_votes` events, voter `sessions` in `abandon_votes`, and new block fields (STATUS `decoupled`; HELM `shield_power`, `thrust_scale`, `torque_scale`; ENGINEERING `shield_focus`): a version 3 peer would drop the new types and misread the blocks. Version 3 added Ack snap −1 (need a full snapshot), long section lengths, the age in every NEAR record, the little-endian LAN beacon, the client limits below and the voice fields (Welcome `lang`, Voice `part` and `last`, the `voice_line` event).

## Transport

- One WebSocket connection per client, binary messages only. The server listens on `--bind ADDR --port N` (WS, default 47801); the static HTTP server for web stations, when on, listens on N − 1 (D108; see Static HTTP).
- Every protocol message is split into chunks of at most 16 KiB of payload (FT-NET-038). A chunk has an 11-byte header, little endian: stream u8, msg_id u32, index u16, count u16, length u16. Streams: 0 control (handshake, lobby, commands, acks, events), 1 snapshot, 2 voice.
- A sender queues all chunks of a message together in one lane, so per stream they arrive contiguously. The receiver keeps one partial message per stream and drops it when another message starts on that stream; malformed chunks and messages over 8 MiB are errors. The server closes a connection once it has sent 16 malformed messages (`NetTransport.MAX_ERRORS`, code 4003).
- Clients send only on stream 0; a chunk of another stream is malformed. A client message may be at most 64 KiB (`NetTransport.MAX_CLIENT_MESSAGE`); a longer one is dropped as malformed. A connection without a session (no accepted Hello) is closed 5 s after it opened (code 4003, `HELLO_TIMEOUT_US`), and at most 16 such connections are open at once (`MAX_SESSIONLESS`): further ones wait in the listen backlog until one gets a session or closes.
- Each connection has two lanes. The high lane (control, events, snapshots) is FIFO; the low lane (voice) is served only when the high lane is empty, one chunk per pump, so voice never delays a snapshot by more than one chunk.
- **Bundles.** All chunks one pump may send to a client go out as one WebSocket message of at most 48 KiB, a concatenation of whole chunks. Receivers split it by the length field (`NetChunker.feed_packet`).
- The server keeps `WebSocketPeer`'s 64 KiB buffer defaults; bundles and chunks stay under them. Web clients raise `inbound_buffer_size` to 1 MiB (D108); `NetClient.inbound_buffer_size` is where.

### Close codes

| Code | Meaning |
|---|---|
| 1000 | Normal: the server's close after a Bye, or a client's own close. |
| 1001 | Server stopped. |
| 4000 | Hello rejected (after HelloRejected). |
| 4001 | Session taken over by a newer connection with its token. |
| 4002 | A send failed: the socket write failed (D106). |
| 4003 | Protocol error: a second Hello, 16 malformed messages, or no Hello within 5 s. |
| 4004 | Queue full: more than 256 KiB queued for a client without a view key. |

The server lets the client close first: it closes 1 s after the last queued message left (`NetTransport.CLOSE_LINGER_US`), and drops a connection still closing after 5 s (`CLOSE_TIMEOUT_US`); 4002 and 4004 close at once. Codes 4000–4004 are `NetTransport.CLOSE_*`.

### Packets per message (known limit)

Godot's `WebSocketPeer` writes each frame's 2–4 byte header and its payload in separate `send` calls, and the server sets `TCP_NODELAY`, so every WebSocket message costs two TCP packets (S9, "Wi-Fi"). GDScript can't change that write path, and turning Nagle back on would trade it for delayed-ACK stalls of up to 200 ms. The cheap part is done: bundling makes it one WebSocket message per client per pump instead of one per protocol message, so a pump that sends a snapshot plus events costs two packets, not two per message. The rest needs an engine change (write header and payload in one `send`); #4 measures the airtime on Wi-Fi.

## Encodings

Every message starts with a u8 type (`NetProtocol.Type`).

- **Snapshots** (type 12) are packed binary (below): they are 30 Hz traffic and the bandwidth budget (R15, S9) needs fixed point and dead reckoning.
- **Every other message** is the type byte followed by `var_to_bytes` of a Dictionary, decoded with `bytes_to_var` (which never builds objects) and checked against `NetProtocol.SCHEMAS`: every field present with its Variant type, no other field, else the message is dropped. These are rare (handshake, lobby, commands at human rates, events), so a self-describing encoding costs little, keeps the schema in one table, and needs no hand-written codec per message. Commands carry the sim command as a Dictionary (`SimCommand.to_dict()` fields), validated field by field on the server (`CommandGate`).

## Lobby, claims and the pause

**Lobby (T043).** The catalogue (`StationViews`, one `StationDef` each) is the six stations, Tactical (Helm + Weapons), Systems (Engineering + Science), Ops (Relay + Comms), Captain and Viewer, plus `all` with `--dev-all-stations`; the other 12 joint views come with M2 (FT-JNT-004). Each player holds one pick; any number may share a station or joint view; one Captain per ship (CLASH-10; a Captain within grace still holds the seat). The coverage check (`NetCoverage`) passes with at least 3 crew players (1 with the dev flag) and all six stations covered; Captain and Viewer don't count. The sim doesn't step until a ship starts: Ready{true} from any crew player of a ship that passes coverage starts it, and the universe steps from the first Start (D129; with several crewable ships, #11 decides whether every ship must start). Snapshots flow before the start and during a pause at 30 Hz of wall clock while anyone holds a pick, re-encoded from one copy of the unchanged world.

**Claims (T044).** Claimable items: `flight` (Helm: `helm_input` with face, decoupled, all-stop, Align; dock and jump when they exist), `shield_facing` (Helm: shield focus), `mount:N` (Weapons: aim, fire, guided fire and ammo type), `crew:N` (Engineering: dispatch and recall). A claimed item takes commands only from its claimer (`claimed` otherwise); an unclaimed one from anyone at its station. A player alone on a station holds all its free items; when a second player joins, the first keeps them, implicit ones included, and the newcomer claims only what the first releases (D130). Claims are released by ReleaseClaim, by a pick change that no longer covers the item's station, and when the claimer's grace ends. Every other control is ship-wide, last writer wins (target selection included, approved in #6): `pips:K` (set_pips per subsystem kind), `shield` (set_shield), `boost` (Engineering), `target` (Helm's target selection). The OWNERSHIP snapshot section names claimers and last writers to the entries of that station (`NetViewState.claimer(item)`, `last_writer(control)`). Claims and `claim_rule` apply in the lobby too: a command on an item another player holds is refused at once before Start; accepted commands queue and apply on the first tick after Start.

**Grace and pause (T045).** A dropped session keeps its pick and claims (not its abandon vote: only connected crew vote) for `--grace-s` (10 s), timed on the server's wall clock, also while paused. When the grace ends, the session lapses: its pick and claims are released and remembered, and if a started ship still in play (not destroyed, retreated or abandoned) then fails coverage, the whole universe pauses (only a grace expiry starts a pause; other changes only update or end one): the sim doesn't step, snapshots keep flowing, and every client gets `pause`. During a pause the paused ship's crew may change picks freely; outside it, a Pick or Release that would make a passing ship in play fail coverage is refused (`breaks_coverage`). The universe resumes (`resume`) once no ship in play fails coverage: a rejoin, a takeover, a pick change, or abandoning the ship. Captain and Viewer never count, so their drops never pause.

**Abandon (D128).** During a pause each connected crew player of the paused ship may vote or withdraw; when the votes exceed half of them (2 of 2), or at once when the host sends Abandon, the ship is abandoned: it leaves play, the pause ends, and a logged server command (`AbandonShipCommand`) makes the sim mark it ABANDONED and give it a LOSS, which ends the M1 encounter. Votes clear when the pause ends; a vote cast in one pause doesn't carry into the next. A vote is evaluated only when cast (a voter who drops loses the vote; the others aren't abandoned by someone else's drop; approved in #6). The abandoned ship's crew commands get `ship_abandoned`. **Run abandon (D241).** Outside a pause, in a co-op session (PvP: a forfeit of that ship, below), the host's Abandon or a passing AbandonVote makes the server submit `AbandonRunCommand` (every crewed ship in play ABANDONED, a LOSS each), broadcast `abandoned` (`by` `host` or `vote`) and clear the votes; `run_over` (outcome `loss`), the debrief (result `abandoned`) and the "Run again" vote follow.

**Marks, pings and alert level (#7, D171).** Per-ship crew state kept by the server outside the sim (no command log, no state hash): `CrewMarks` (8 marks, alert level) and `CrewPings` (rate limit, copy), handled by `NetCrewState` (its `on_alert`, `on_mark` and `on_ping` are ServerSession handlers). A mark records the session that placed it: crew stations rename, move or delete only their own, Relay any; the Captain only fills empty slots. A mark attached to a contact stays attached when the contact is lost or destroyed; clients show its last known position. A ping pulses its item for 3 s on every screen of the ship; another station's ping on the same item within that time is a silent copy (`copy` names the first pinger). Marks and pings may name only a contact of the sender's faction or one it detects, and a named site the world has (a `SiteTable` row); an undetected contact and an id past the ship count get the same `bad_mark` or `bad_ping`, so the refusal doesn't tell the ship count. Mark names lose control and bidi characters. `NetCrewState.reset(ship)` clears marks and pings and sets the alert to Normal, with events (the run reset calls it).

**Main screen (E03).** The ship's main-screen view is crew state kept outside the sim like the alert (`NetCrewState.main_views`, rules in `MainScreen`): the Captain sets it, Relay only while no Captain pick exists (connected or within grace); a run reset puts it back to forward. The status view reads the CAPTAIN section, STATUS and the `alert` event; a ping of kind `card` names a Comms card (a card id of the ship's board, 0 to the number of cards posted; the event carries a `card` object, `kind` (StoryTable.Kind), `title` and `detail` (text keys) and `expires` (s left, −1 none), so the main screen can draw it without the COMMS section).

**Relay (E02).** `CrewRelay` keeps, per ship and outside the sim like marks, the hazard zones and scan positions (MARK items outside the 8 marks that survive Hard, FT-SPA-028), Relay's four routes, the inbox of marks other ships sent and the ship's log; `NetCrewState` answers MarkSend and MarkAccept and the Mark ops above and writes the log from sim events (`LOG_EVENTS`) and its own actions. Probes, the lane switch and the probe launcher are sim state (`RelayTable`, `ProbeTable`, `ProbeSystem`; commands `launch_probe` {x, y, z}, `flag_lanes` {on} and Engineering's `fabricate_probe`, no fields) and Relay claims the launcher as item `probe`. A flagged lane crossing a friendly or neutral ship raises the sim event `lane_warning` (`other` = that ship, `value` = mount index) to Weapons and Relay before the shot (FT-RLY-011). `ProbeSystem.coverage_at(world, faction, pos)` answers whether a deployed probe of the faction covers a point (P13). Subsystem marks ask Science's scan knowledge (`ScienceKnowledge.weak_points`).

**Run reset (D178, FT-M1-012).** After a crewed ship's outcome every station shows the outcome card (`run_over`). Each connected crew player of the ship may cast or withdraw a RunAgain vote; when the votes exceed half of them, or at once when the host sends `true`, the server builds the world again from the encounter (`NetServer.restart_run()`: a fresh command log, every client's next snapshot full and its ticks restarting at 0), clears marks, pings and the alert (`marks`, `alert`), drops the ship-computer lines still queued, and puts the ship back in the lobby (`lobby` `started` false) with picks and claims kept; the crew presses Start again. Votes are evaluated when cast; a voter who drops loses the vote. In M1 the reset is world-wide (one crewed ship); #11 decides it per ship.

**Rejoin.** A client joining or rejoining during a pause gets the current `lobby`, `pause` and `abandon_votes` events right after Welcome and the Catalogue. A token resumes its session for the server's life (approved in #6). Within the grace everything is as it was. The 64-connection cap applies to every Hello that adds a connection: a new session, a lapsed one, and one resuming within its grace (refused `session_full`; the session keeps its grace). Taking over a still-connected session (a restarted client before its old socket closed) is not refused. A Hello whose token's grace has just run out lapses the session first (pick and claims released), even if it is then refused. After it, the session gets its ship back and its pick if still allowed (the Captain seat may be taken), else that ship's pick screen (Welcome `ship` set, `entry` ""); its old claims come back where still free.

## Multi-ship sessions and PvP

Version 8 (M4, #11; owner M4-Q1 to M4-Q10, 2026-10-28). Code: `net/net_fleet.gd` (`NetFleet`, the server's lobby of ships and the session rules), `net/fleet_messages.gd` (`FleetMessages`, every payload below and its `check()`), `sim/run/session_rules.gd` (`SessionRules`: modes, team win rule, relaunch policies, eliminated-crew destination). Every server sends these events; a world the server can't rebuild (the M1 and load encounters) keeps its fixed ships and refuses ShipAdd, ShipTeam and SessionMode with `lobby_closed`.

**Lobby (M4-Q3, M4-Q4, M4-Q6).** Any player adds a ship (ShipAdd), up to 6; a ship nobody picked vanishes at Start. Each ship has its own picks and coverage check, as in `lobby`. In teams and holdout lobbies a crew puts its ship on team 0 or 1; any split with at least one ship a side. The host picks the mode and, in teams, the win rule (last team standing or first to finish). The universe starts all together once every crewed ship has pressed Start, each passing its coverage check; `fleet.waiting` lists the crewed ships that haven't. A ship's `started` in `lobby` stays false until the universe starts (a press alone shows in `fleet.ships[].started`). PvP sessions (every mode but co-op) offer no host pause (FT-MIS-040). Each lobby change rebuilds a lobby world of allied placeholder ships (ids stay, picks are kept) and sends the Catalogue again. At Start the server builds the world from the ships with a crew pick, in lobby order (`RunSetup.slots`), with the mode's factions and teams, so lobby ship ids may change: every session holding a pick gets `picked` with its ship's new id (even an unchanged one), a session whose ship vanished gets `picked` ship −1, and the Catalogue and `fleet` carry the new ids.

**Takeover in a pause (M4-Q8, FT-NET-042).** Takeover {ship, entry} may come from a player of an allied ship (same faction) and from the paused ship's own Captain and viewers; no accept prompt, the first claim wins, and every session of the ship's side gets `takeover`. Refusals: `enemy_ship` (a hostile ship's player), `taken` (the entry covers no station still uncovered: someone claimed it first), `breaks_coverage` (the taker's own ship in play would fail coverage), `not_paused`.

**Elimination, handover and relaunch (FT-MIS-011, FT-MIS-012, FT-MIS-030, D91, M4-Q2, M4-Q10).** A destroyed, abandoned or forfeited ship leaves play (`eliminated`) and its run progress resets; a later pause on another ship waits only for ships still in play. In PvP every abandon (Abandon, AbandonVote, in a pause or outside one) is a forfeit, `eliminated` reason `forfeit`. The server eliminates a crewed ship when its run status leaves in-play. Two ticks later, unless the session is over (then the crews stay for the debrief and "Run again"), every session on it gets `handover`, then `picked` for its move: by default to the main screen of the first surviving friendly ship as a viewer, or to the lobby scoreboard (no pick) when none survives or the mode sends them there (race and last ship standing). A side whose relaunch policy allows it may relaunch: the eliminated ship's connected crew, as they were at elimination, vote by more than half (Relaunch); the server then submits `RelaunchShipCommand`, and once the sim accepts it the crew are back on their stations and everyone gets `relaunched`. The server reads elimination, relaunches, kills and finish times from the run state (`RunTable`), so every world gets these events, not only director runs whose sim emits `eliminated` and `session_over`; the raw sim events of those names go to nobody. PvP kills on the scoreboard count crewed ships of another side destroyed by the ship (`RunTable.kills`).

**Session outcome.** `session_over` names the winners and the reason (`SessionOutcome`): co-op `objective` or `all_lost`; race `first_to_finish`; last ship standing `last_standing`; teams by the host's rule; holdout `holdout_over`, scored by `held_s`.

## Handshake and sessions

1. The client sends Hello. The server reads `v` before anything else, so a client of any version gets `HelloRejected{version_mismatch}` (FT-NET-005); a Hello of the right version that fails the schema gets `bad_hello`.
2. A Hello with a known token resumes that session (same id, pick and event stream; a connection still holding it is closed with code 4001). Otherwise the server opens a session with a new 128-bit token. Every Hello that adds a connection, new or resumed, is checked against the session cap first (`ServerSession.admit_rule`, T046; see Rejoin).
3. Welcome then Catalogue. A session with a pick gets a full snapshot next.

A session's grace is `--grace-s` (10 s) after its connection drops (`NetSessions`); its token stays valid after that (see Rejoin above).

## Snapshots

Header: u8 type (12), u8 flags (bit 0 full), u32 seq, u32 tick, u8 n sections; then n sections of u8 kind, length, payload; the length is a u16, or 0xFFFF followed by a u32 for a section of 65,535 bytes or more (`SnapshotBuilder.put_length`), so no section is ever dropped. A delta omits sections with nothing to say.

A view key is (ship, catalogue entry, difficulty toggles) (FT-NET-040). Each section is encoded once per snapshot per owner (a ship, or a faction for contacts), each view key's message once, and all clients of a key get the same chunks. Deltas chain on the previous snapshot of the stream; a client that misses one (a stall) gets a full snapshot instead (FT-NET-037). Clients check that a delta's seq follows the last one applied. A client that can't apply a snapshot refuses deltas until the next full one and asks for it with Ack snap −1 (`NetViewState.need_full`).

Fixed point (`NetCodec`): positions 1/16 m as int32 offsets in the scenario's cube, wrapped into [−P/2, P/2) (D104, D124); velocities 1/16 m/s int16 (±2,048 m/s); angular velocities 1/50 rad/s int8; orientations smallest-three in 32 bits; projectile velocities 1/8 m/s. Dead reckoning is integer arithmetic on both ends, so they agree bit for bit; residuals and predictions use the minimum image with P from Welcome, so a contact crossing a seam costs a small residual.

## Discovery

The LAN beacon (`net/lan_beacon.gd`, FT-NET-012) is one UDP datagram broadcast to 255.255.255.255:47790 once a second; `LanBrowser` lists a host until 3.5 s after its last datagram. A server bound to a loopback address sends none (no other machine could join it), and neither does one started with `--no-beacon`. Ports: WebSocket 47801, HTTP 47800 (WS − 1, D108), discovery 47790 (UDP).

The datagram is little-endian and append-only: a newer format adds fields at the end, and a parser reads the fields it knows.

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | magic "FTLB" |
| 4 | 1 | beacon format (`LanBeacon.FORMAT` = 1) |
| 5 | 4 | protocol version u32 |
| 9 | 2 | WebSocket port u16 |
| 11 | 2 | HTTP port u16, 0 when the server doesn't serve the web export |
| 13 | 1 | players connected |
| 14 | 1 | player cap |
| 15 | 1 | flags: bit 0 a session is active (`NetServer.session_active()`: any session connected or within its grace; the pid file's `session_active` means the same) |
| 16 | 1 | name length n (UTF-8 bytes, at most 63) |
| 17 | n | server name, UTF-8 |

## Static HTTP

`StaticServer` (`net/static_server.gd`, FT-NET-030, FT-NET-039) serves the web export from `--http-root DIR` on the bind address at the WebSocket port − 1. It answers GET and HEAD only, prefers `<file>.br` when the request accepts brotli (browsers offer it over HTTPS only), falls back to `<file>.gz` when it accepts gzip, serves HTTPS and WSS when started with `--tls-cert` and `--tls-key` (D294), and sends an ETag with `Cache-Control: no-cache`, so a reload gets 304. It answers one byte range (`Range: bytes=a-b`, `a-` or `-n`: 206 with `Content-Range`; unsatisfiable: 416) of the file itself, never of its `.gz` (Safari fetches the keep-awake video that way), and serves `.mp4` (`video/mp4`, H.264, for Safari) beside `.webm`. A file whose name carries a 10-digit hex content hash (`index.<hash>.wasm`, `.pck` and the audio worklets, renamed by `tools/release/web_patch.py`) is sent `Cache-Control: public, max-age=31536000, immutable`, so a returning browser reuses its wasm and pack without asking (D197); every other file keeps `no-cache` and an ETag. The server polls it once a frame within a 400 µs budget; the request head search resumes from where it stopped.

## Session log

`SessionLog` (`net/session_log.gd`, D199) is the server's append-only log, JSON Lines: `{"t": seconds since it opened, "kind": ..., ...}`. `--session-log PATH` sets the file (`off` writes none; default `user://logs/session-<unix time>.jsonl`). Other systems write to it through `NetServer.session_log` (null until `start_session_log()`): `event(kind, fields)` for something that happens rarely, `count(name, n)` for something that happens often (the final `summary` line holds every counter), `close(extra)` at the end. Lines the server writes:

| kind | fields | when |
|---|---|---|
| `start` | `port`, `bind`, `protocol` | the log opens |
| `join` | `session`, `name`, `client` (desktop, web, bot), `resumed` | after each accepted Hello |
| `snapshot_age` | `pooled` and `clients[]`: `n`, `age_p50_ms`, `age_p99_ms`, `gap_p99_ms` (clients also `session`, `name`, `client`, `ua`, and `fulls` and `stalls`, the full snapshots and stalls on its current connection so far: a device that keeps resyncing shows here) | every 10 s with snapshots in the window |
| `coop` | `coop` (`chip_sent`, `chip_answered`, `chip_declined`, `chip_expired`, `shortcut_shared`, `mark_used`, `probe_scan`; `scan_option` from #10), `pair` (`p1` to `p15`, spec §7.3), `ship`, and the event's own fields (`chip`, `event`, `mark`) | each cooperative event (FT-PAIR-013); `NetCoop`; the counters `coop.<pair>.<kind>` are in the summary |
| `long_frame` | `session`, `name`, `client`, `ms`, `what` | each ClientFrame (#28) |
| `summary` | `counters` (`commands` and whatever other systems count), `snapshot_age` over the whole session (same shape, plus `unmatched` per client), `tick` | the server quits |

Snapshot age is the client's arrival time (before decoding, taken when the game polls its socket, so a throttled phone's frame gaps count) minus the server's capture stamp (a re-encoded idle state counts from its encode time), joined by snapshot seq as in D161. Clients on other machines have another clock: the server takes the smallest `server receive time - client send time` over a client's reports as that clock's offset, which includes the quickest uplink trip, so ages read at most that trip (a few ms on Wi-Fi) too high. Percentiles come from 1 ms histograms (values above 3 s count as 3 s). Gaps are between a client's consecutive arrivals. #13's M4 check reads `snapshot_age.pooled.age_p99_ms < 150` from the summary of a real Wi-Fi session.
