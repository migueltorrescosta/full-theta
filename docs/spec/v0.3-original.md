# Project Specification: Cooperative 3D Space Adventure

Version: 0.3
Status: Initial implementation planning

## 1. Objective

Build a cross-platform, LAN-based, cooperative 3D spaceship game loosely inspired by EmptyEpsilon.

Players occupy the same physical room, using separate computers or displays to operate different stations aboard one shared spacecraft. Each station provides a specialized view of the same authoritative simulation.

The game combines Newtonian space combat, exploration, ship operations, branching missions, synthetic voices, and meaningful crew coordination.

The visual style is colorful, exaggerated, retro science fiction with simple, cartoon-like 3D assets.

The coding agent must convert this specification into a dependency-aware DAG of executable tasks before beginning broad implementation. Each task must have explicit prerequisites, measurable acceptance criteria, and verification procedures. Identify unresolved decisions and obtain approval for significant architectural choices.

## 2. Core requirements

The game must support cross-platform desktop clients, LAN multiplayer, mixed displays, keyboard and mouse, controllers, and touchscreen input where practical.

Use offline multilingual text-to-speech. Speech recognition is explicitly excluded. Players communicate naturally in the same room, supported by visual cues and audio alerts.

The game must not require a human game master. Procedural adventures must combine reusable, handcrafted scenario components with branching missions and an adaptive director.

The intended session lasts 20–40 minutes. Players explore, receive missions, communicate with NPCs, fight enemies, earn resources, and upgrade their ship. Ship destruction resets all run-specific progression.

## 3. Engine and architecture

Evaluate Godot 4, Unity, and Unreal Engine. Godot 4 is the preferred initial candidate because it is free, open source, cross-platform, and supports multiplayer and headless execution. Confirm the choice through a technical proof of concept.

Use one authoritative simulation per session. Separate simulation, networking, station interfaces, input, audio, missions, and presentation.

The simulation owns physics, ship state, weapons, damage, resources, enemy behavior, mission outcomes, and progression. Clients send validated gameplay commands and receive authoritative state changes and events.

Use data-driven definitions for ships, weapons, subsystems, upgrades, enemies, dialogue, and scenarios.

Pin engine and dependency versions. Prefer free, offline-capable tools and procedural assets.

## 4. Stations

The six logical stations are:

**Helm:** Forward cockpit, navigation, orientation, velocity, and three-dimensional thrust-based flight.

**Weapons:** Manual aiming, target selection, switchable 3D views, weapon mounts, firing arcs, range, and weapon limitations.

**Engineering:** Power distribution, impulse energy, maneuverability, subsystem condition, heat where applicable, and active repairs.

**Science:** Sensor analysis, enemy vulnerabilities, anomalies, environmental hazards, and uncertain information.

**Relay:** Probes, contact coverage, communications, mission opportunities, and external interactions.

**Captain:** Optional coordination, mission priorities, strategic decisions, and engagement policies.

Stations must be independently usable and combinable. The Captain must never be mandatory for normal gameplay.

## 5. Flight, combat, and damage

Implement full three-dimensional Newtonian movement, including thrust, inertia, momentum, rotation, and ship-specific maneuvering capabilities.

Weapons must have physical positions and orientations. Firing must respect mount geometry, valid firing arcs, range, cooldowns, ammunition, energy, and subsystem condition.

Support a varied arsenal, including projectile weapons, energy beams, missiles, and torpedoes.

Subsystems such as shields, engines, weapons, and sensors must suffer independent damage with direct gameplay consequences.

All important state changes must generate immediate, visible feedback. For example, Engineering must receive an alert when shields fall to 40%. Relevant stations must receive appropriate visual warnings when attacked or affected by system failures.

Enemy AI should eventually support flanking, coordinated attacks, retreat, subsystem targeting, and tactical adaptation. Implement basic, testable behaviors first.

Never secretly manipulate damage, physics, or enemy statistics to force a desired outcome.

## 6. Pairwise cooperation

Cooperation is a defining gameplay requirement. Six logical stations create 15 possible pairs, and every pair must have at least one meaningful cooperative mechanic.

Routine actions must remain possible independently, but cooperation should improve effectiveness, safety, information, or mission outcomes.

Information must be asymmetric. Stations must possess different knowledge and capabilities, giving players natural reasons to communicate.

The game must use contextual visual cues and audio alerts rather than speech recognition or constant artificial dialogue prompts.

Required pairwise mechanics:

| Pair | Cooperative mechanic |
|---|---|
| Relay + Science | Deploy probes, analyze discoveries, expand sensor coverage, and unlock communications opportunities. |
| Science + Weapons | Identify shield frequencies and vulnerabilities; configure weapons to exploit them. |
| Engineering + Helm | Balance impulse power, turning authority, and system resources to execute maneuvers. |
| Helm + Weapons | Align weapon mounts, maneuver into firing arcs, and balance attack positioning against evasion. |
| Helm + Science | Position the ship for scans, observations, and safe anomaly investigation. |
| Helm + Relay | Navigate to contacts, approach docking points, and select routes through hazards. |
| Weapons + Engineering | Balance firepower, energy, heat, ammunition, and defensive systems. |
| Weapons + Relay | Coordinate engagement decisions using hostile intent, mission objectives, and communications. |
| Engineering + Science | Diagnose unknown damage, radiation, anomalies, and environmental effects. |
| Engineering + Relay | Evaluate docking, repairs, resupply, and mission opportunities against ship condition and resources. |
| Captain + Helm | Coordinate interception, retreat, rendezvous, and mission priorities. |
| Captain + Weapons | Set engagement priorities, ammunition policies, and collateral-damage constraints. |
| Captain + Engineering | Decide whether to commit emergency resources or sacrifice systems. |
| Captain + Science | Evaluate uncertain discoveries and decide whether further investigation justifies the risk. |
| Captain + Relay | Choose negotiation strategies, accept contracts, and manage mission branches. |

Each pair must have defined independent capabilities, asymmetric information, cooperative advantages, feedback, consequences, and fallback behavior.

Create these interactions through shared simulation systems rather than 15 unrelated minigames. Cooperation failures should usually impose costs rather than make the game arbitrarily unplayable.

## 7. Missions and progression

Initial scenarios must include enemy waves and rescue missions. Support exploration, branching encounters, negotiations, and additional scenarios through reusable mission components.

The adaptive director manages pacing, encounters, threats, and opportunities. It may change which events occur but must not secretly manipulate simulation rules.

Missions must offer consequential choices and clear outcomes.

Players may earn money, salvage, repairs, and upgrades during a run. Upgrades must create distinct ship builds.

Ship destruction resets all run-specific progression. Permanent unlocks and cosmetic persistence are not yet confirmed.

## 8. Audio and presentation

Use offline synthetic voices for NPC radio conversations, ship-computer announcements, alerts, and appropriate crew-related dialogue.

Support multiple spoken languages at launch, subject to confirmation of the exact languages.

Dialogue must use structured player choices. TTS must support appropriate prioritization and interruption so critical alerts remain audible.

Use a distinctive retro sci-fi, cartoon-like visual style with simple geometry and readable ship silhouettes.

## 9. First playable milestone

Build one playable encounter with at least two networked station clients and one authoritative simulation.

The milestone must include:

1. A controllable ship with Newtonian movement.
2. Helm, Weapons, and Engineering interfaces.
3. One enemy with basic functional AI.
4. Manual aiming and a directionally constrained weapon mount.
5. A damageable and repairable subsystem.
6. One complete cooperation loop, preferably Engineering + Helm.
7. Immediate event notifications and synchronized station state.
8. A clear encounter outcome and complete run reset.
9. Automated tests and documented launch instructions.

Establish architectural interfaces for the remaining stations without requiring them all to be fully implemented in this milestone.

## 10. Reference research and licensing

Inspect EmptyEpsilon's source code and documented behavior to understand station interactions, ship definitions, weapons, and scenario logic.

Record which mechanics are reproduced, redesigned, or omitted. Do not blindly copy its architecture.

EmptyEpsilon uses GPL-2.0 licensing. Review applicable obligations and track the provenance and licenses of reused code, assets, and content.

## 11. Coding-agent workflow

Before broad implementation, produce a DAG containing unique task IDs, dependencies, deliverables, acceptance criteria, tests, risks, and required approvals.

Prioritize research, architecture, networking, physics, and TTS feasibility. Build the first playable vertical slice before expanding the full game.

Include automated tests for simulation, weapon geometry, damage, networking, mission transitions, run resets, and all 15 station pairs.

Maintain a requirements-to-tests traceability map. Keep implementation tasks small, reviewable, and independently verifiable where practical.

The agent must not silently resolve major ambiguities or make unapproved architectural changes.

## 12. Outstanding decisions

Identify and request clarification on the maximum player count, hosting model, initial TTS languages, interpretation of the 20–30% death-risk target, information-sharing rules, absent-station behavior, scenario authoring format, EmptyEpsilon compatibility expectations, and the precise victory/defeat model.

Do not block low-risk research or prototypes on decisions that can safely remain open.
