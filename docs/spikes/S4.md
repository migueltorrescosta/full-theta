# S4: WebSocket snapshots under loss, token reconnect, backpressure and chunking

Run on fugaku (i7-11800H), 2026-10-19, Godot 4.7.2-stable, for T019 and TECH-2 (R4; FT-NET-004, FT-NET-025, FT-NET-037, FT-NET-038). Code in `spikes/s4/`, unit tests in `tests/spikes/s4/`.

## Setup

One headless Godot server (`TCPServer` plus `WebSocketPeer.accept_stream`) and 8 headless Godot client processes. The server ticks a stub sim at 60 Hz: 6 ships and 40 contacts. Half the contacts move, ship subsystems change every 0.5 s, and each ship has a static name, loadout, cargo and a 2048-float layout block. The server sends snapshots at 30 Hz and emits one reliable event every 12 ticks (5 Hz). Clients run at 60 frames/s, the server at 120.

All processes, server and clients together, are pinned to CPUs 2 and 3 (`taskset -c 2,3`). This stands in for the issue's 2 cores (`taskset -c 0,1`), because another spike owns CPU 0. Loss comes from `tc netem loss 2%` on the loopback of a private network namespace (`ft-s4`), never on the host's `lo`. That loopback has its MTU set to 1500, so messages segment as they would on Ethernet or Wi-Fi rather than in 64 KiB loopback packets. Netem on `lo` drops each packet once with probability 2 %, and every packet crosses `lo` once, so both directions see the loss: server-to-client data, client acks and TCP ACKs.

Snapshot age is the client's receive time minus the server's send stamp, both from `Time.get_unix_time_from_system()` in microseconds on the same host. `Time.get_ticks_usec()` counts from each process's own start, so it has no common base across processes. The server stamps a snapshot when it builds it, so the age includes the server's queueing, the network and the client's frame phase (up to 16.7 ms at 60 frames/s).

Codec: `var_to_bytes` Dictionaries, the quickest option. T040 picks the final codec. A full snapshot is 68.3–68.7 kB and a delta is 2.96 kB on average.

## Protocol in the spike

Every message travels in chunks of at most 16 KiB of payload, each with a 9-byte header (stream u8, msg id u32, index u16, count u16). Small messages are one chunk. Each client has a send queue with two lanes. The high lane is FIFO and carries control messages, events and snapshots, so events and snapshots keep their order. The low lane carries voice. The server serves the low lane only when the high lane is empty, and then at most one voice chunk per server frame. Before each chunk, the server checks that the peer's outbound buffer has room for it.

Snapshots are full on join, resume and resync. Otherwise each is a delta against the newest snapshot the client is sure to hold: the higher of the last snapshot it acknowledged and the last full snapshot sent (TCP keeps order). The server encodes each (snapshot, base) delta once and shares it among clients on the same base. In the 60 s runs it encoded about 2,000 deltas for 14,000 sends, which is the FT-NET-040 idea with one view key. Clients ack the newest applied snapshot and the newest event delivered, once per frame when either changes.

Events carry a sequence number and the tick. The server keeps them until every live or in-grace session has acknowledged them. The client's inbox delivers them in order and exactly once, dropping duplicates (`S4EventInbox`).

## Results

### 1. Snapshot age under 2 % loss (FT-NET-004): met

Four 60 s runs, 8 clients each, with no kill, stall or voice. A1–A3 ran before the last fix to the lag count (`S4Resync.lag()`, which restarts at one after a resync), and B2 did too. A4 and B3 ran on the final code.

| Run | Snapshots | p50 ms | p99 ms | max ms | Loss-induced resyncs |
|---|---|---|---|---|---|
| A1 | 14,002 | 12.7 | 49.8 | 675.7 | 6 |
| A2 | 13,917 | 7.5 | 41.1 | 649.0 | 2 |
| A3 | 14,050 | 9.6 | 49.1 | 749.3 | 1 |
| A4 | 14,063 | 4.6 | 48.8 | 653.9 | 1 |
| Pooled | 56,032 | 9.6 | 48.7 | 749.3 | 10 |
| No loss, 30 s | 6,859 | 10.3 | 15.0 | 31.5 | 0 |

The pooled p99 of 48.7 ms meets the < 150 ms criterion with margin. The tail is TCP's: 0.46 % of snapshots are older than 150 ms, the p99.9 is 377 ms, and 4 of the 32 client runs have their own p99 above 150 ms (the worst is 233 ms). Each tail event is a lost segment waiting for a retransmission timeout, which is at least 200 ms on Linux and doubles when the retransmit is lost too. Every snapshot queued behind the lost segment on that connection then waits as well (head-of-line blocking). Without loss, a client's age is nearly constant at 5–15 ms, set by the phase between its frames and the server's.

Lost acks and retransmission timeouts also tripped the stall detector 10 times in 32 client-minutes (limit: 15 unacknowledged snapshots, 500 ms, D106). Each trip cost one extra full snapshot of 68 kB and no lost event.

The server's frame work stayed at a median of 1.1–1.3 ms per second-long window and a maximum of 2.6 ms. Each client received about 88 kB/s, which is 5.6 Mbit/s for all 8.

### 2. Token reconnect (FT-NET-025): met

Runs B2 and B3 killed client `c7` with SIGKILL at 15 s and restarted it 1 s later with its token file. From the restart to the first applied full snapshot took 202 ms and 195 ms (B1 before a fix: 192 ms), including Godot's start-up. The criterion is 2 s. In each run the server resumed the session, and the seat (ship and station) matched the one stored with the token. The new process's event cursor began at 79, the last event the killed process had delivered and acknowledged, so the stream has no hole. A process that dies between delivering an event and acknowledging it sees that event again after the restart: delivery is at least once across a crash, and exactly once within a process.

The server notices the dead socket on its next poll after the kernel closes it. It keeps the session for the 10 s grace period (FT-NET-033) and lets a valid token take over a session whose old socket is still open.

### 3. Stalled reader (FT-NET-037, TECH-2): met

Client `c6` stopped calling `poll()` for 2 s at 30 s, with 2 % loss:

| | B2 | B3 |
|---|---|---|
| Server marked it stalled after | 532 ms | 527 ms |
| Deltas sent between stall start and detection | 15 | 15 |
| Deltas sent after detection | 0 | 0 |
| Resync full snapshot sent after the client resumed | 32 ms | 28 ms |
| Client recovered (full snapshot applied) after resuming | 50 ms | 50 ms |
| Full snapshots needed | 1 | 1 |
| Held events carried by that full snapshot | 8 | 8 |
| Event gaps or missing delta bases | 0 | 0 |

On resume the client first applies the 15–17 deltas still in the kernel buffers (ages up to 2 s), acks them, and then receives one full snapshot. Recovery needs one full snapshot, and the event sequence numbers run contiguously across the stall in every client of every run.

Detection relies on acks. `WebSocketPeer.get_current_outbound_buffered_amount()` stayed at 0 throughout the stall: `send()` writes straight into the kernel socket, and a loopback socket's kernel buffers hold far more than 2 s of deltas. So the server marks a client stalled when it has more than 15 snapshots unacknowledged, when a send fails, when more than 256 KiB of its high lane is queued, or when its outbound buffer is above 48 KiB while high-lane data waits. The last condition needs both parts. In an earlier run (B1), a voice burst filled the outbound buffer to 52 kB while no snapshot was waiting and caused a needless resync, so a full buffer alone no longer counts. Once the client has acknowledged everything sent and its high lane is empty, the server sends one full snapshot with every event after the client's acknowledged one. The client drops the duplicates.

### 4. Chunking and buffer defaults (FT-NET-038): met

`WebSocketPeer` defaults, read at runtime: `inbound_buffer_size` 65535, `outbound_buffer_size` 65535, `max_queued_packets` 4096, `heartbeat_interval` 0 (no keep-alive pings), `encode_buffer_max_size` 8 MiB. The probe (`spikes/s4/s4_probe.gd`) sends single unchunked messages over loopback:

| Message | Sender outbound buffer | Result |
|---|---|---|
| 16,393 B, 60,000 B, 65,535 B | default | delivered |
| 70,000 B (a full snapshot) or 132,440 B (the voice clip) | default | `send()` returns `ERR_OUT_OF_MEMORY` (`wsl_peer.cpp`: queued + size > `outbound_buffer_size`) |
| 70,000 B or 132,440 B | raised to 1 MiB | sent, but the receiver closes the connection with code 1009 (message too big) |

Without chunking, both a full 6-ship snapshot and a 3 s clip fail unless both ends raise their buffers. In the runs, the voice test queues a 3 s 22.05 kHz mono 16-bit clip (132,440 B as a message, 9 chunks) for `c5`, and then forces a full snapshot (68 kB, 5 chunks) in the same frame. The arrival order at the client was the same in B2 and B3:

`S0/5 S1/5 S2/5 S3/5 S4/5 V0/9 V1/9 V2/9 V3/9 S0/1 V4/9 V5/9 V6/9 V7/9 S0/1 V8/9`

The full snapshot left first although the clip was queued before it, and the next two delta snapshots slipped between voice chunks. The clip arrived intact (SHA-256 checked) 62–83 ms after queueing, far shorter than its 3 s of playback. The first voice chunk arrived 29–32 ms after queueing.

## Limits and notes

- Bandwidth: about 88 kB/s per client with `var_to_bytes` deltas (2.96 kB, mostly per-field type tags and string keys for 26 moving entities). That's 5.6 Mbit/s for 8 clients, and about 45 Mbit/s if scaled to 64, well above R15's 10 Mbit/s. S9 and T040 need a packed codec (quantised positions, numeric field ids) or per-view filtering.
- The voice test builds its sine clip in GDScript on the server's main loop. That build took one 17 ms frame in the B runs, which counts against the test harness, not the transport. S7b's Piper subprocess avoids it.
- Loopback hides airtime. The age tail here is purely TCP retransmission behaviour. Wi-Fi (R10, #4) adds contention, so the harness should be rerun there.

## How to run

```bash
godot=$(tools/get-godot.sh); $godot --headless --path . --import
spikes/s4/netns.sh up 2 1500             # namespace ft-s4, 2 % loss, MTU 1500 (sudo)
spikes/s4/netns.sh exec spikes/s4/run.sh /tmp/s4/a --run-for 60               # criterion 1
spikes/s4/netns.sh exec spikes/s4/run.sh /tmp/s4/b --run-for 60 \
  --kill c7@15 --stall c6@30 --voice c5@45                                    # criteria 2–4
spikes/s4/netns.sh down
$godot --headless --path . -s res://spikes/s4/s4_probe.gd -- --port 47819     # buffer probe
```

`netns.sh exec` runs a command in the namespace as `$USER`, pinned to `S4_CPUS` (default `2,3`). `run.sh` starts the server and N clients, writes `server.log`, `c*.log` and `summary.md` (from `aggregate.py`) into the output directory, and passes anything after `--` to the server. Server flags, with defaults: `--port 47810 --ships 6 --contacts 40 --layout-floats 2048 --tick-hz 60 --snapshot-hz 30 --run-for 60 --log PATH --lag-limit 15 --grace-s 10 --chunk-size 16384 --voice-to NAME --voice-at S --voice-seconds 3 --voice-per-pump 1 --max-fps 120 --seed 1`. Client flags: `--url --name --token-file --log --run-for --stall-at --stall-for --launched-us --max-fps`. `run.sh` takes timestamps from bash's `EPOCHREALTIME`, because the uutils `date` on fugaku drops leading zeros in `%6N`.

To extend: S3 can serve its HTTP files from the same process and point a web client at `ws://host:47810`. S7b queues Piper output with `S4SendQueue.push(S4Chunker.STREAM_VOICE, bytes)` in place of `_queue_voice`. S9 can raise `--clients` (in `run.sh`) and `--ships`, and use the `stats` lines in `server.log`, which give frame work and bytes per client every second.

## Decisions

Approved in #4 (D106):

- Criterion 1 is read as the p99 pooled over all clients on loopback (48.7 ms, pass). Per-client p99 exceeded 150 ms in 4 of 32 client runs; per-device p99 is the #4 Wi-Fi check.
- The stall trigger is more than 15 unacknowledged snapshots (500 ms), a failed send, or a high-priority queue over 256 KiB. It isn't the outbound buffer, which stays empty on loopback.

Still provisional:

- Chunks hold 16 KiB of payload, voice gets one chunk per server frame, and events share the snapshot lane.
- An unknown or expired token gets a new seat. FT-NET-026's fall back to the pick screen belongs to T045.

## For promotion (#6, T045)

Promote `S4Chunker`, `S4SendQueue`, `S4Resync`, `S4EventInbox` and `S4Sessions`. They are small classes with no sockets and unit tests in `tests/spikes/s4/`; their FT ids stay pending until then. The server and client scripts are harnesses. Size the buffers from the measured numbers: a full snapshot of 68 kB and a delta of 3 kB under this codec. Keep the 64 KiB `WebSocketPeer` defaults and chunk anything above 16 KiB, because a browser client's inbound limit can't be relied on to be raised.
