# S9: 64 connections across 6 ships

Run on fugaku (i7-11800H, 16 threads, `powersave` governor with turbo), 2026-10-19, Godot 4.7.2-stable, for T023 and TECH-9 (R15; FT-GEN-001, FT-GEN-003, FT-NET-008, FT-NET-028, FT-NET-040). Code in `spikes/s9/`, unit tests in `tests/spikes/s9/`.

## Setup

One headless Godot server process runs the S6 load in its main thread: `S9World`, which is `S6WorldPacked` with 100 ships and 500 projectiles at 60 Hz, ships 0–5 being the player ships. The same thread accepts and polls the WebSocket connections, builds the snapshots at 30 Hz and sends them, with the S4 transport (`S4Chunker`, two-lane send queue, `S4Resync` stall detection). The server runs at up to 120 frames/s and is pinned to CPUs 0 and 1 (`taskset -c 0,1`).

The 64 connections come from 8 headless Godot processes with 8 WebSocket connections each, pinned to CPUs 8 and 9. They stand in for 64 remote devices. Seats: the 36 crew fill the 6 stations of each of the 6 ships, and the 28 viewers are dealt round the ships (5, 5, 5, 5, 4, 4). Each connection logs every snapshot's age and size and acks at most 5 times a second. The first connection of each process also decodes every snapshot into a view state; one run decoded on all 64.

The processes share a private network namespace `ft-s9` whose loopback has an MTU of 1500 and no loss, so its `/proc/net/dev` counters hold only this run's packets.

Two limits of the host apply to every run below:

- CPUs 0 and 1 are the hyperthread siblings of CPUs 8 and 9 (`thread_siblings_list` 0,8 and 1,9), so the server shares its two physical cores with the simulated clients.
- During the runs, another project's numerical experiment kept 2 to 4 threads busy at 100 % without pinning, and other spikes ran browsers and Godot processes. The load average was 3 to 13. CPUs 0 and 1 weren't reserved, so the scheduler also placed that work there.

Measurements:

- **Server tick:** the wall time of each server frame that ran a sim tick (60 a second; the frames in between only poll and pump): poll, sim step, snapshot build and queueing, and the pump that hands chunks to the sockets. Every other tick frame also builds a snapshot ("snapshot frames"). The main thread's `/proc/thread-self/schedstat` splits each frame into time on a CPU and time preempted (waiting on a run queue).
- **Snapshot age:** the client's receive time minus the server's build stamp, both unix microseconds (as in S4). It includes queueing, the network and the client's frame phase (up to 16.7 ms at 60 frames/s).
- **CPU:** the server's `utime + stime` from `/proc/self/stat` over the measured window, as a share of 2 cores.
- **Bytes:** payload bytes per client as the server hands them to `WebSocketPeer` (9-byte chunk header plus the message), and the namespace's loopback bytes and packets, both directions, with every header.

Each run measures 60 s, starting 3 s after all 64 clients have joined (about 4 s after the server starts).

## Codec and view keys

A view key is (ship, catalogue entry, difficulty-toggle set). A snapshot message is assembled from sections, and each section is encoded once per snapshot for its owner (a ship or a faction):

| Section | Owner | Content | Sent to |
|---|---|---|---|
| Own | ship | position, velocity, orientation, angular velocity, every snapshot (26 B); 16-byte top-bar status block when it changes | every entry |
| Engineering | ship | 48-byte subsystem table when it changes | Engineering |
| Contacts | faction | position and velocity of every known ship | every entry (disc radar on every station, FT-STN-002; Relay map; callsign rail) |
| Near | ship | orientation and angular velocity of contacts within 2 km | Helm, Weapons, viewer (they draw ship models) |
| Projectiles | ship | live projectiles within 1 km | Helm, Weapons, viewer (tracers) |

The status and subsystem blocks are stand-ins of a plausible size, since S6 has no ship systems. They change twice a second and on each hit. A faction knows every ship within 20 km of one of its player ships, which is all 100 in the S6 arena. The runs are co-op: all 6 ships form one faction. Every crew station is its own key, and the viewers of a ship share one, so the 64 clients hold 42 keys.

Encoding:

- Fixed-point: positions in 1/16 m as int32 (site-local offsets), velocities in 1/64 m/s as int16, angular velocities in 1/50 rad/s as int8 (±2.54 rad/s; the runs used 1/100 rad/s, which caps at ±1.27 rad/s, below S5's 90°/s roll cap, so the unit was coarsened afterwards; the field is still one byte per axis, so the sizes and bandwidth below stay valid). Orientations use smallest three in 32 bits (worst error under 0.2°). Ids are u16.
- Contacts are dead reckoned. Server and client both extrapolate a contact as $\hat x = x_k + \mathrm{round}(v_k\,(t - t_k))$ in integer units, so they agree bit for bit. The server sends a contact again only when $\max_i |x_i - \hat x_i|$ exceeds 0.5 m, as a residual against $\hat x$ (int8 or int16 per axis) plus the velocity change. Near orientations work the same way, extrapolated with the last sent angular velocity, with a 1° tolerance. One orientation model per faction serves all its ships' near sections, so each contact is checked once per snapshot.
- Projectiles fly straight. Each is sent once, when it enters the range or its id is reused, with its position and velocity (20 B). Clients extrapolate it, and ids that leave or die are listed as gone.
- Deltas chain on the previous snapshot of the same key. TCP delivers in order, and a client that misses a snapshot (stalled, `S4Resync`) gets a full snapshot of the current model instead. So all clients of a key take the same bytes, and the server builds each key's chunk once and queues the same buffer for each of them (`S9SendQueue.push_chunk`).
- A message has a 19-byte header (type, flags, seq, tick, and an 8-byte send stamp that only the age probe needs), then per section 3 bytes of kind and length.

Typical sizes in the runs: a delta is 150 B for Science, Relay and Comms, 160 B for Engineering, and 229 B for Helm, Weapons and viewers. A full snapshot is 2.4 kB, or 3.6 kB with the near and projectile sections.

`tests/spikes/s9/test_s9_codec.gd` checks the quaternion and kinematic round trips, the integer rounding, and that four views joining at different times hold exactly the server's model after 90 snapshots, with every contact's dead-reckoned position within the tolerance of the true one. It also checks that a key's message is assembled once and shared, and that projectile refires are seen.

Where a tick frame goes in r2 (means per tick frame): sim 1.73 ms, snapshot 0.90 ms (1.8 ms per snapshot frame), pump 0.42 ms, poll 0.20 ms. A snapshot build costs about 1.1 ms on a quiet host: filtering (known contacts, near sets and projectile ranges) 0.39 ms, contacts 0.24 ms, near 0.22 ms, own and projectile sections 0.26 ms, and 42 view-key messages 0.22 ms. Queueing the 64 sends adds about 0.5 ms.

Snapshot age is far inside 150 ms in every run: the pooled p99 is 16–28 ms (63 ms in D2), and the worst single connection's p99 is 65 ms. No client stalled, no full snapshot was needed after joining, and no decode failed.

The tick criterion depends on the host. With the host quiet, the mean is 3.3 ms and the p99 is 5.8–6.5 ms. With 2 to 4 unpinned busy threads also landing on CPUs 0 and 1, the p99 rises to 16–23 ms. Most of that is preemption: the preempted p99 is 8.5–14 ms. The rest is slower work: the on-CPU time grows by about half, because the busy hyperthread siblings and the lower turbo clock slow the same code. The sim alone went from 1.7 ms to 2.3–3.5 ms per tick. Read as the mean and the p99, like S6's budget (D104), the criterion is met on a quiet host and not met under this contention. The on-CPU p99 alone is 7.9–10.5 ms under contention. The owner accepted the quiet-host runs (r2, t2) as the pass, with the loaded runs recorded as a caveat; #11's 64-connection gate re-verifies the tick (#4).

### 2. One encode per view key, bandwidth (TECH-9, FT-NET-040): met

Per snapshot the server encodes 25 sections (6 own, 6 Engineering, 6 near, 6 projectile, 1 contacts) and assembles 42 view-key messages, one per distinct key, for 64 sends. Without sharing, that would be 64 filtered encodes. The 6 viewer keys serve 28 clients.

Payload per client, run C2 (C1 and C3 are within 1 %):

| Entry | Clients | B/s per client (mean) | Range |
|---|---|---|---|
| Helm | 6 | 6,711 | 6,225–7,195 |
| Weapons | 6 | 6,711 | 6,225–7,195 |
| Viewer | 28 | 6,700 | 6,225–7,195 |
| Engineering | 6 | 4,888 | 4,874–4,912 |
| Science, Relay, Comms | 18 | 4,574 | 4,571–4,581 |
| All | 64 | 5,934 | 4,571–7,195 |

| Run | Payload, server to clients | Loopback wire total, both directions | Packets/s |
|---|---|---|---|
| C1 | 3.05 Mbit/s | 7.15 Mbit/s | 8,398 |
| C2 | 3.04 Mbit/s | 6.82 Mbit/s | 7,935 |
| C3 | 3.06 Mbit/s | 7.07 Mbit/s | 8,252 |

Both totals are under 10 Mbit/s: the payload is 3.0 Mbit/s, a 15th of the 45 Mbit/s that S4's `var_to_bytes` codec would need for 64 clients. The wire total of 6.8–7.2 Mbit/s counts every IP, TCP and WebSocket header in both directions, and headers are more than half of it. A 3 s capture (`tcpdump` in the namespace) shows why. Godot's `WebSocketPeer` writes each frame's 2–4 byte header and its payload in separate `send` calls, so with `TCP_NODELAY` every message takes two packets: about 1,900 header packets and 2,100 data packets a second from the server. The clients send about 3,100 bare TCP ACKs a second. Acking each snapshot from the client (S4's choice) took another 3,600 packets a second and 1.4 Mbit/s, so the clients here ack at most every 200 ms. That is enough for the 15-snapshot stall limit.

The simulated clients used 8–11 % of CPUs 8 and 9 with one decoding connection per process, and 15–17 % with all 64 decoding.

### Codec settings

The offline probe (`spikes/s9/s9_bench.gd`, 900 snapshots, no sockets) shows that the tolerances matter little. Most of a delta is fixed: the header, the section framing and the own-ship block.

| Contact tolerance | Orientation tolerance | Near / projectile range | Helm, viewer delta B | Relay delta B | Full B (Helm) |
|---|---|---|---|---|---|
| 0.25 m | 0.5° | 2 / 1 km | 264 | 181 | 3,633 |
| 0.5 m (runs) | 1° | 2 / 1 km | 229 | 150 | 3,633 |
| 1 m | 2° | 2 / 1 km | 201 | 125 | 3,633 |
| 1/16 m | 0.01° | 2 / 1 km | 648 | 254 | 4,084 |
| 0.5 m | 1° | 4 / 2 km | 347 | 150 | 7,043 |

Without dead reckoning, every contact would be sent every snapshot: 100 contacts at about 9 B each is 0.95 kB per delta, and 50 near orientations add 0.45 kB for Helm, Weapons and viewers. For this seat plan that is about 18 Mbit/s. Dead reckoning is what keeps the budget.

### Rerun on an idle host (CPU clock)

After the review fixes (`096c56c`), the 64-connection run was repeated with fugaku idle (load average 0.3–0.9, no foreign job). The tick got slower, not faster:

| Run | Host | Tick mean / p99 / max ms | Sim per tick ms | Preempted p99 ms | Snapshot age p99 ms |
|---|---|---|---|---|---|
| Q1 | idle | 5.3 / 10.5 / 12.5 | 2.87 | 0.03 | 20.2 |
| Q2 | idle | 6.2 / 10.4 / 11.8 | 3.29 | 0.03 | — |
| Q3 | idle, clients on CPUs 4,5 | 7.0 / 11.0 / 13.1 | 3.70 | 0.04 | — |
| Q5 | CPUs 0,1,8,9 with energy preference `performance` | 4.5 / 11.7 / 39.4 | 2.27 | 4.15 (another job started) | 21.5 |

Nothing preempted the server in Q1–Q3, yet the sim alone took 2.9–3.7 ms per tick, against 1.1 ms for the same 100 ships and 500 projectiles in S6's continuous benchmark run minutes later on CPU 0. Sampling `scaling_cur_freq` during a run showed CPUs 0 and 1 at 0.8–1.8 GHz: with the `powersave` governor and `balance_performance` energy preference, a 60 Hz loop that sleeps between frames never earns turbo clocks, while a busier host (the earlier r2 and t2 runs at load 4–6) kept them higher. Bandwidth, encodes per key and snapshot age are unchanged (3.06 Mbit/s payload, 6.6–6.9 Mbit/s wire, p99 age 20–22 ms).

So the tick budget depends on the host's CPU clock policy as much as on the code. A laptop host on a power-saving profile will see the slower numbers. The owner therefore treats the tick criterion as not met (D111, amending D109): T041 (#6) encodes and sends snapshots on a worker thread from a copy of the state, so the sim tick holds only the sim (about 1.7–3.7 ms here). The TECH-5 burst fallback is D110 (subtitles only beyond 4 queued lines).

## TECH-5 combined run

Criterion: the server, one rendering client and a burst of 6 synthesised lines keep the tick under 8 ms and the p95 line audible under 1 s. **Not met for the line latency; the tick is met on the S7b sim server and missed on this server, on a shared host.** Details are in `docs/spikes/S7b.md`.

This load ran with 63 simulated stations (`--procs 9 --conns 7`) on CPUs 0, 1, 8 and 9. Its `--extra` command started the S7b run on CPUs 6 and 7: a sim server with the S6 world (100 ships, 500 projectiles) and 4 persistent Piper processes, and a rendering Godot client under `xvfb-run` with llvmpipe that plays each clip. That client is the 64th connection on the host, but it connects to the S7b server, not to this one (provisional simplification). Events fired in bursts of 6 free-text lines every 6 s, 50 lines in all, each clip streamed per sentence.

| | Q2 (host load 5) | L2 (load 5–11, a foreign 12-worker job running) |
|---|---|---|
| This server's tick frames, mean / p99 / max ms | 4.5 / 10.5 / 12.5 | 3.5 / 8.5 / 16.7 |
| S7b sim tick during the run, mean / p99 / max ms | 1.5 / 3.7 / 8.0 | 2.1 / 6.0 / 17.7 |
| Line audible, p50 / p95 / max ms | 929 / 1,768 / 2,322 | 1,365 / 2,588 / 3,185 |

Without bursts (one line per second, 64 stations), lines were audible at p95 422 ms (load 4–8) and 739 ms (load 11), while this server's tick p99 was 17 ms in both runs. This server's tick exceeds its quiet-host 6 ms p99 whenever the host is busy, Piper or not, so the excess comes from host contention (clock, SMT siblings, foreign jobs), not from synthesis on other cores. The burst misses 1 s because 6 lines need about 2 CPU-seconds of synthesis on 2 shared cores. The fallbacks are in S7b.md.

## Limits and notes

- **Scenario:** S6's ships fly assisted between waypoints, mostly in straight lines with turns at each waypoint. A dogfight with constant manoeuvring sends more contact records, up to the 1.4 kB worst case above. The S6 arena (100 ships in a 4 km cube) is denser than a real scene, so near and projectile sections are larger here than they would be in play.
- **Factions:** co-op is one contacts section for all 6 ships. A PvP session with 2 factions has 2, at about 100 B per snapshot each. Different difficulty-toggle sets per ship would only add keys if they change a section's fields. Here the toggles are part of the key but change no field.
- **Wi-Fi:** loopback hides airtime. On Wi-Fi the packet rate (about 8,000 a second, half of it 2–4 byte WebSocket headers and bare ACKs) costs more airtime than the bytes do. #4 should measure it. A fix belongs in the transport: write the header and payload in one `send`, which may need an engine change or a different WebSocket write path.
- **Projectiles** are sent only within 1 km, as spawn records. Tracers further out, and hits, would come as events, which S9 doesn't send.
- **Clients:** the simulated stations decode the snapshots but don't render. S7b's run adds one rendering client (TECH-5).

## How to run

```bash
godot=$(tools/get-godot.sh); $godot --headless --path . --import
spikes/s9/netns.sh up                           # namespace ft-s9, loopback MTU 1500 (sudo)
spikes/s9/netns.sh exec spikes/s9/run.sh /tmp/s9/C1 --run-for 60
spikes/s9/netns.sh down
$godot --headless --path . -s res://spikes/s9/s9_bench.gd -- 900 0.5 1.0 2000 1000   # offline codec probe
```

`run.sh OUT_DIR` starts the server on CPUs 0 and 1 and the 8 client processes on CPUs 8 and 9. It waits for the server to finish, then writes `server.log`, `p*.log` and `summary.md` (from `aggregate.py`) into the output directory. Flags, with defaults: `--run-for 60` (measured seconds), `--port 47830`, `--procs 8`, `--conns 8`, `--decode 1` (decoding connections per process), `--server-cpus 0,1`, `--client-cpus 8,9`, `--extra CMD`, `--extra-conns N`, and anything after `--` goes to the server. Server flags: `--ships 6 --world-ships 100 --projectiles 500 --factions 1 --toggles normal --pos-tol 0.5 --rot-tol 1 --near-range 2000 --proj-range 1000 --snapshot-hz 30 --lag-limit 15 --warmup 3 --join-timeout 30 --max-fps 120 --seed 1`. Outside the namespace the run works too, but the loopback counters then include other traffic.

For the combined host run with S7b (TECH-5): `--extra CMD` runs `CMD` through `bash -c` once the load has started, with `S9_URL` (`ws://127.0.0.1:47830`) and `S9_OUT` set. `--extra-conns N` makes the server wait for those N connections before the measured window. The extra client joins like the others: a hello in an `S4Chunker` control chunk holding `var_to_bytes({"t": "hello", "proto": 9, "name": ..., "ship": 0, "entry": "viewer"})`. Snapshots then arrive as `S9Views` messages, which `S9ViewState.apply` decodes, and the server's summary lists that client with the others. To stay at 64 connections (FT-GEN-003), run 63 simulated stations: `--procs 9 --conns 7 --extra-conns 1` (36 crew and 27 viewers, plus the rendering client).

## Decisions

Provisional unless marked approved:

- Station field sets (`S9Views.SECTIONS`): every entry gets the own-ship block and all faction contacts (the disc radar is on every station). Helm, Weapons and the main screen add near orientations and projectiles, and Engineering adds the subsystem table. Science, Relay and Comms get only contacts here, since their cards and boards change by events.
- Deltas chain on the previous snapshot of the same key, not on each client's acknowledged snapshot as in S4. TCP keeps order, and a stall leads to a full snapshot anyway (FT-NET-037). This keeps exactly one encode per key; an acked base would need one per key and base.
- Clients ack at most every 200 ms, and at once after a full snapshot.
- Dead-reckoning tolerances of 0.5 m and 1°, a near range of 2 km and a projectile range of 1 km.
- The tick criterion is read as the mean and the p99 per 60 Hz tick frame, as in D104, on a quiet host (approved in #4). The age criterion is read as the p99 pooled over all clients (D106).

## For #6 (T040, T041, T042)

- **Codec:** promote `S9Codec` (fixed point, integer dead reckoning, smallest-three quaternions, residual records) and the section idea: per-owner sections encoded once per snapshot, and view-key messages assembled from them. The view-key cache and the shared chunk (`S9SendQueue.push_chunk`) belong with `S4SendQueue` in T045. At promotion, `quant_pos` takes the site-local offset as three 64-bit floats (a `PackedFloat64Array`, D104) instead of a float32 `Vector3`.
- **View keys:** (ship, catalogue entry, toggle set); 42 keys for this seat plan. The joint views (FT-NET-032) are unions of their stations' sections, so they add keys but no new sections.
- **Measured limits:** 3.0 Mbit/s of payload and 6.8–7.2 Mbit/s on the wire for 64 clients. About 1.1 ms per snapshot build plus 0.5 ms to queue 64 sends on a quiet host. The full tick frame is 3.3 ms mean and 6 ms p99 on a quiet host, so it leaves about 2 ms of p99 headroom against 8 ms for the rest of the server (damage, AI, HTTP, events). Snapshot age is under 30 ms p99 on a quiet host (63 ms pooled and 65 ms for the worst connection in the most disturbed run).
- **If the tick budget is missed on a host:**
  - Encode and send on a worker thread from a copy of the section inputs, which takes about 2.5 ms out of each snapshot frame. The sim stays single-threaded (FT-ARC-006). This costs a state copy and thread-safety work in T041.
  - Send viewers at 15 Hz. This saves 28 of 64 sends on alternate snapshots but no builds, and halves the main screen's update rate.
  - Move snapshot building and sending to the frame between sim ticks (the server runs at 120 frames/s). This shortens the longest single frame but not the work per 60 Hz period, and adds about 8 ms of age.
