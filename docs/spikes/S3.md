# S3: single-threaded web export of one station over WebSocket

Run on fugaku (i7-11800H), 2026-10-19, Godot 4.7.2-stable, Playwright 1.64.1 with Chromium headless shell 156 (SwiftShader WebGL). Covers T021 and TECH-3 (R3; FT-NET-030, FT-NET-033, FT-NET-039, FT-NET-046, FT-AUD-017). Code in `spikes/s3/`, unit tests in `tests/spikes/s3/`. Device checks (tablet fps, touch, sleep) belong to #4 (T022).

The machine was shared: another session's unpinned Python jobs kept the load average at 10–16 and ran on the CPUs this spike used (server on CPUs 2 and 3, browsers, curl and Godot clients on 4, 5, 12 and 13). Browser timings are therefore pessimistic, and the tick runs were repeated with the server at real-time priority to separate HTTP's own cost from preemption.

## What was built

| Part | Files | Role |
|---|---|---|
| Static server | `s3_static_server.gd` (`S3StaticServer`) | Non-blocking HTTP/1.1 on `TCPServer` in the server's main thread: GET and HEAD, MIME types (`application/wasm` for wasm), `<file>.gz` with `Content-Encoding: gzip` when accepted, ETag with `Cache-Control: no-cache` (reloads get 304), single byte ranges, keep-alive. `poll(budget_us)` stops once the budget has passed, and each connection writes at most one 64 KiB slice per poll, read from the file as it goes. |
| Spike server | `s3_server.gd` | Extends the S4 server script (no copy): the S4 WebSocket server, snapshots, events, tokens and voice lane, plus the static server, an Engineering model per ship (`S3StationSim`, `S3EngineeringModel`), `cmd` and `voice_req` messages, an S6 sim load (`S6WorldPacked`, 30 ships and 150 projectiles) each tick, and a per-tick log. |
| Panel | `s3_engineering.tscn`, `s3_engineering.gd`, `s3_link.gd` (`S3Link`) | Power pips for ENG, WPN, SHD, SNS and MAN within a reactor cap of 12, a heat bar per system, both from snapshots; + and − send commands. "Tap to enable audio" unlocks Web Audio, starts the keep-awake and asks for a 1.2 s chime on the voice lane. The token is kept in `localStorage`. |
| Keep-awake | `s3_keep_awake.gd` (`S3KeepAwake`) | Plays a 771-byte muted looping VP9 video, started from the tap and restarted when the page becomes visible; uses the Screen Wake Lock API instead in a secure context. |
| Web shell | `s3_shell.html` | Godot's default shell without its secure-context check (see below). |
| Build | `build.sh`, `s3_keepawake_frames.gd` | Exports the preset, patches one line of the engine's `index.js`, makes the video, writes `.gz` copies and prints sizes. |
| Harness | `harness/harness.mjs`, `harness/debug.mjs`, `run.sh`, `aggregate.py` | Playwright modes `join`, `refresh`, `idle` and `multi`; the tick-delay run and its summary. |

`export_presets.cfg` has a Web preset "S3 Engineering web" (no threads, no GDExtension, custom feature `s3`, VRAM compression for desktop and mobile) and `project.godot` sets `run/main_scene.s3`, so the game exports are unchanged.

## Plain http:// needs two workarounds

Research (tech.md §2.7) expected a no-threads build to run from a plain `http://` LAN page. Godot 4.7.2 doesn't, for two reasons, and the spike works around both:

1. The default HTML shell refuses to start outside a secure context ("Secure Context - Check web server configuration (use HTTPS)"), even for a no-threads build. `s3_shell.html` drops that one check.
2. The engine's audio start-up loads the sample-position AudioWorklet unconditionally, and `AudioContext.audioWorklet` exists only in secure contexts, so start-up fails with "Cannot read properties of undefined (reading 'addModule')". `build.sh` guards that call in `index.js` and fails if the pattern isn't found. Without AudioWorklet, Godot mixes through its `ScriptProcessorNode` fallback (deprecated, runs on the main thread), and sample playback, the web default, can't start, so the panel's player uses stream playback.

`127.0.0.1` and `localhost` count as secure contexts, which would hide both problems. The harness therefore maps the host name `s3.lan` to 127.0.0.1 in Chromium, so the page is `http://s3.lan:47820/` and `isSecureContext` is false, as on a LAN.

A third trap: in the browser, Godot's `WebSocketPeer` buffers incoming messages itself and drops what doesn't fit its 64 KiB `inbound_buffer_size` ("Buffer payload full! Dropping data."). One 68 kB full snapshot already overflows it, so `S3Link` sets it to 1 MiB. This is client-side and under our control, unlike the server-side limits S4 measured.

## Results

### 1. Web export served over HTTP, connects over WS (FT-NET-030): met

The Godot server serves the export from `build/s3/` on port 47820 and the WebSocket on 47821, in one process and thread. The page derives the WebSocket URL from its own host name (`?ws=PORT` overrides the port). Every join below loaded the page from that server and joined over WS.

### 2. Headless Chromium joins in < 10 s and plays; audio after a tap (FT-AUD-017): met

Join time is navigation start to the first applied snapshot (`performance.now()` in the page), with a fresh profile, so the whole 10.4 MB gzip download is included.

| Run | Network | Join ms | fps mean (min) over 30 s | Audio context before / after tap | Peak level after tap | Tap to clip playing ms | "+" to snapshot showing it ms |
|---|---|---|---|---|---|---|---|
| join 1 | loopback | 1,759 | 28 (16) | suspended / running | 0.365 | 155 | 57 |
| join 2 | loopback | 1,265 | 40 (30) | suspended / running | 0.365 | 160 | 50 |
| join 3 | loopback | 1,452 | 28 (3) | suspended / running | 0.220 | 1,405 | 629 |
| join 50 | 50 Mbit/s, +5 ms | 4,620 | 15 (6) | suspended / running | 0.365 | 221 | 59 |
| idle run | loopback | 1,247 | – | suspended / running | 0.365 | 74 | – |

The harness wraps Web Audio before the page loads and routes everything connected to the output through an analyser. Before the tap, the context is suspended and silent; after a touch tap on the button, it is running and the chime reaches the output at its full amplitude (0.366 of full scale). The clip's SHA-256 matched every time. Join 3's lower peak and slow tap ran while foreign jobs loaded the browser CPUs; the clip still played to the end.

The fps column is SwiftShader on four shared cores, indicative only; device fps is checked in #4. The 50 Mbit/s profile throttles HTTP through the DevTools protocol as a rough stand-in for Wi-Fi.

### 3. Refresh-to-rejoin and keep-awake (TECH-3; FT-NET-033, FT-NET-046): measured; idle met

Each setup reloads the page 10 times, 3 s apart. "Reload to snapshot" runs from the harness's reload call to the first snapshot on the new page. The grace period must cover the server's view: from the old socket's close to the token's resume, read from the server log.

| Setup | Reload to snapshot mean / max ms | Server: drop to resume mean / max ms | Same seat |
|---|---|---|---|
| Memory cache, loopback | 3,678 / 5,112 | 2,214 / 3,499 | 10 of 10 |
| Disk cache, loopback | 3,821 / 4,917 | 2,144 / 3,128 | 10 of 10 |
| Disk cache, 50 Mbit/s | 4,388 / 5,806 | 2,539 / 3,360 | 10 of 10 |
| Memory cache, 50 Mbit/s | 4,030 / 4,854 | 3,107 / 3,717 | 10 of 10 |

The browser closes the old socket only once the new page's HTML has arrived, so the server-side gap is shorter than the reload as the user sees it. Most of the time is engine start-up (compiling the 39.5 MB wasm and booting), 2.5–4.5 s here on contended CPUs. On a quieter moment earlier the same disk-cache reloads took 1.2–2.4 s. A Playwright context's memory cache doesn't keep the 10 MB wasm, so every reload downloads it again; with a disk cache, as a tablet has, every file revalidates with 304.

Every reload rejoined the same seat within the 10 s grace. The worst server-side gap was 3.7 s, so 10 s leaves a margin of about 2.7 times for slower tablets and Wi-Fi. A tablet compiles wasm several times slower than this laptop, so #4 should time reloads on the owner's devices before the grace is shortened.

Keep-awake: after the tap, a 10 min idle session (no input) stayed connected. The socket was open in all 60 status lines (every 10 s), the page applied 17,847 snapshots, the server logged no drop until the harness closed the page at 602 s, and the video was playing in all 20 samples (every 30 s). Headless Chromium doesn't sleep or lock as a tablet does, so this shows only that the mechanism runs for 10 min without disturbing the connection. Whether it keeps an iPad or Android tablet awake is #4's check. The video is VP9 WebM, the only encoder in the ffmpeg on fugaku; older iPads may not play it. An H.264 MP4 would cover Safari, and `S3KeepAwake` already lists `keepawake.mp4` first if it exists.

### 4. Six simultaneous joins, sizes and tick delay (FT-NET-039): met

Export sizes (bytes; images and video aren't recompressed):

| File | Raw | Gzip -9 |
|---|---|---|
| index.wasm | 39,514,754 | 10,084,286 |
| index.pck | 217,800 | 194,513 |
| index.js | 279,858 | 68,400 |
| index.html, worklets, icons, video | 52,057 | 44,313 |
| Total | 40,064,469 | 10,391,512 |

The engine is 97 % of the download; the pck holds the whole project except tests, tools, docs and gdUnit4. Browsers advertise brotli only over HTTPS, so gzip is what plain HTTP gets.

`spikes/s3/run.sh` runs four 40 s phases against one server: no clients; 6 headless Godot S4 clients; the same plus 6 curl loops fetching the gzip export over and over; the same plus 6 headless Chromium pages joining at once and playing for 30 s. Each tick logs its lateness (start minus due time) and the part of that lateness during which HTTP polls ran. The server runs at 1,000 frames/s, with the HTTP poll budget at 400 µs.

| 6 WS clients | 2,394 | 559 / 1,032 | 4 / 8 | 0 | 1,259 / 2,725 | 46 | 0 |

| + 6 browsers | 2,407 | 529 / 1,031 | 42 / 163 | 0 | 1,326 / 4,727 | 642 | 1.5 |

Same run at normal priority:

| Phase | Ticks | Lateness p50 / p99 µs | HTTP share p99 / max µs | Ticks delayed > 1 ms by HTTP | Tick p50 / p99 µs | Longest HTTP poll µs | HTTP MB/s |
|---|---|---|---|---|---|---|---|
| No clients | 2,400 | 485 / 1,018 | 0 / 4 | 0 | 825 / 1,283 | 13 | 0 |
| 6 WS clients | 2,400 | 510 / 1,025 | 2 / 12 | 0 | 908 / 1,685 | 56 | 0 |
| + 6 downloads | 2,396 | 542 / 1,020 | 375 / 558 | 0 | 1,043 / 2,439 | 853 | 323 |
| + 6 browsers | 2,991 | 603 / 5,483 | 74 / 6,519 | 2 | 1,940 / 9,096 | 15,094 | 1.2 |

With six full downloads running flat out (274–323 MB/s in total, each gzip wasm in 0.15–0.39 s), no tick waited more than 0.8 ms for HTTP, and the longest poll was 1.1 ms: the 400 µs budget plus one 64 KiB slice. The two ticks over 1 ms at normal priority fell in polls that took up to 15 ms of wall time: another process held the CPU in mid-poll, which the real-time run rules out. The criterion is met for HTTP's own work. On a host shared with heavy load, any code in the main loop, not only HTTP, can be preempted.

Both runs also show whole-process stalls of 50–530 ms (5 in the real-time run, a few in the other) in every phase, including the idle one, with no HTTP work involved. The machine was swapping (4.5 GB of swap in use) under the foreign load; this is not an HTTP effect, but it shows how loaded fugaku was.

The six browsers joined in 5.5–8.7 s (real-time run) and 9.9–18.3 s (normal run). Six SwiftShader instances on four shared cores render at 3 frames/s, so this measures fugaku's CPUs, not the server: each page received its 10.4 MB in well under a second. Those slow pages ack late, trip S4's stall detector and get resync full snapshots, which is why tick duration rises in that phase (p99 4.7–9.1 ms).

## How to run

```bash
godot=$(tools/get-godot.sh); $godot --headless --path . --import
(cd spikes/s3/harness && npm ci)                    # Playwright 1.64.1, Chromium headless shell 1248
spikes/s3/build.sh [ARTEFACT_DIR]                   # export, patch, video, .gz, size table
$godot --headless --path . -s res://spikes/s3/s3_server.gd -- --run-for 600 --log /tmp/s3.log
cd spikes/s3/harness
taskset -c 4,5,12,13 node harness.mjs join --out join.json            # criterion 2
taskset -c 4,5,12,13 node harness.mjs refresh --reloads 10 --profile /tmp/p --out r.json
taskset -c 4,5,12,13 node harness.mjs idle --minutes 10 --out idle.json
cd ../../..; S3_RT=1 spikes/s3/run.sh /tmp/s3/run --phase-s 40       # criterion 4
```

Server flags beyond S4's: `--http-port 47820 --bind 127.0.0.1 --http-root build/s3 --http-budget-us 400 --http-slice 65536 --http-log 0|1 --tick-log PATH --load-ships 30 --load-proj 150 --clip-seconds 1.2`; S3 changes S4's defaults to `--port 47821 --run-for 600 --max-fps 1000`. Harness flags: `--url`, `--mbps` (throttle), `--profile DIR` (disk cache), `--fps-seconds`, `--reloads`, `--minutes`, `--clients`. `harness/debug.mjs` prints every console line and saves a screenshot. The build for tablets, its README and the raw results are in the issue's artefacts (`s3/`).

A headless Godot process can't draw, so Godot sleeps its low-processor delay (6.9 ms) every frame whatever `max_fps` says, capping a headless server at about 145 frames/s. `s3_server.gd` shortens that delay so `--max-fps` sets the pace; at 1,000 frames/s a tick starts at most about 1 ms after it is due.

## Decisions

Approved by the owner in #4 (D108):

- Plain HTTP works through a custom shell and a one-line guard in the engine's `index.js` at export time (above), with audio mixed by the `ScriptProcessorNode` fallback. #12 adds a test that fails when the patched pattern changes; both problems go upstream to Godot (drafts in the #4 artefacts).
- HTTP and WebSocket listen on separate ports (47820 and 47821); the page finds the WebSocket at its own port plus one.
- The HTTP poll budget is 400 µs per frame, and each connection writes at most 64 KiB per poll.
- Responses carry an ETag with `Cache-Control: no-cache`, so a reload revalidates rather than downloading again, and a new build is picked up at once.
- The keep-awake is a muted looping VP9 video started by the audio tap; an H.264 MP4 is added only if iPads need it in #4, and Auto-Lock settings are documented as the fallback.
- The grace stays at 10 s (D83), re-timed on tablets in #4.
- The browser client's WebSocket inbound buffer is 1 MiB.

## For promotion (#6)

- **Static server:** promote `S3StaticServer` with its tests. Keep the budgeted `poll`, gzip, ETag and ranges; serve the export built from the same commit (TECH-4). Run the poll after the tick and the WebSocket pump, as here. Bind to the LAN address the host picks, not to every interface by default.
- **Keep-awake:** promote `S3KeepAwake` and the video. Add an H.264 MP4 if #4 shows iPads need one, and in any case document the Auto-Lock setting in `docs/launch.md` as the fallback.
- **Web build:** the custom shell and the `index.js` guard belong in the export pipeline (#12), with a test that the guard pattern still matches after an engine upgrade; report both problems upstream to Godot.
- **Client:** raise `WebSocketPeer.inbound_buffer_size` on web clients, and size the stall detector for clients that run slowly: a tablet at low fps acks late and keeps getting full snapshots.
- **Server loop:** set `OS.low_processor_usage_mode_sleep_usec` in the headless server, or the frame rate can't exceed about 145 frames/s.
