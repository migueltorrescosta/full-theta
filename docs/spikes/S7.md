## Licence audit

Each voice's MODEL_CARD names its dataset and licence, and says whether the model was trained from scratch or fine-tuned. Most Piper voices are fine-tuned from the `lessac` (medium, high) or `ryan` (low) checkpoints. The lessac data is under the Blizzard 2013 research licence, which allows research purposes only and excludes "development, marketing, commercialisation, sale or licencing of voice synthesis products"; ryan is CC BY-NC-SA 4.0. A fine-tune inherits weights trained on that data, so whether it is free of those terms is unclear. FT-LIC-007 excludes unclear voices, so this audit uses three statuses (D105, decision 1):

- **Accept**: permissive or public-domain dataset, and trained from scratch (or fine-tuned from an accepted voice).
- **Unclear**: permissive dataset, but fine-tuned from lessac, ryan or an unidentified base. Not shipped (D105).
- **Exclude**: the dataset itself is non-commercial or research-only.

The `rhasspy/piper-voices` repository is MIT; the table gives the dataset licence and the base each card names. "Mimic 3" is MycroftAI/mimic3-voices (CC BY-SA 4.0 repository, CC BY 4.0 per voice).

## Real-time factor

RTF = synthesis time / audio duration over the 20 lines of the voice's language, with the model loaded and one warm-up line synthesised first. Each run is a fresh process: "1 core" is `taskset -c 4` with one ONNX thread, "2 cores" is `taskset -c 4,5` with two. Load is `PiperVoice` construction (ONNX session) with the model already in the page cache; a cold disk read adds to it. First line is the warm-up line on one core (npc01, 5–6 s of audio).

- Medium voices meet tech.md §4.1's estimate (RTF 0.05–0.2): a 5 s line takes under 0.6 s on one core. High voices are about 9 times slower: fine for build-time prerendering (2,000 lines × 3 languages × 3 s at 0.66 is about 3.3 core-hours, or 15 minutes on 16 cores) but not for runtime free text on one core within FT-AUD-015's 1 s.
- Loading a voice takes 0.9–1.7 s, so a per-line process would spend most of the 1 s budget on loading. Keep one loaded process per voice (FT-AUD-019).
- Without a thread setting, onnxruntime starts one thread per CPU it sees: the render run used 16 CPU-minutes in 2.3 minutes on 4 pinned CPUs. Set `intra_op_num_threads` explicitly on a shared host.

## Ship-computer filter

The ship computer uses the same Piper voices (D71) with a flatter delivery (`noise_scale` 0.333, `noise_w_scale` 0.333, `length_scale` 1.05) and this chain in numpy (`robotic` in `spikes/s7/s7.py`), no extra system package:

| Step | Setting | Effect |
|---|---|---|
| Ring modulation | 70 Hz sine, 35 % wet | Buzz under the voice |
| Feedforward comb | 6 ms delay, gain 0.45 | Hollow, metallic resonance |
| Band-pass | 300–3,400 Hz, zero-phase FFT, 150 Hz cosine edges | Intercom bandwidth (99.7–99.9 % of energy in band afterwards) |
| Light bitcrush | 2-sample hold, 6-bit quantising, 30 % wet | Digital grit |
| Normalise | Peak 0.9 | Even level |

The parameters are a first guess for the owner to judge (T018); each is one constant.

## Stitching

For each voice, 5 sentences render three ways: the whole sentence at once (`-full`); fragments synthesised separately, trimmed at a 0.02 amplitude threshold with 10 ms padding and joined with 70 ms gaps (`-stitched`); and the stitched version through the computer filter. The fragments cover the D101 cases: a number ("sessenta e dois"), a ship class and name ("Aurora Sete"), a digit-by-digit bearing, a caller's name ("Kessler Nove"), a place name, and a gendered number in pt_PT ("Restam | duas | naves inimigas", against "dois torpedos"), which needs per-gender fragment variants.

Over the 30 pairs, stitched lines run 0.43 s longer than whole ones on average (from 0.39 s shorter to 2.77 s longer, the longest being the seven-fragment bearing line). Each fragment is synthesised as its own utterance, with utterance-final intonation, so stitching is expected to sound choppier for NPC speech than for the filtered computer. The owner judges naturalness (T018).

## Pronunciation notes

- espeak-ng switches language for English words: "Full Theta" is read as English inside pt_PT lines, but as Italian "tˈɛta" in it, and "Halcyon" as "ˈaltʃjon". Closed-set names need per-language phoneme overrides (Piper accepts `[[ phonemes ]]` inline).
- `en_US-norman-medium`'s config uses the espeak voice `en` (British phonemes), as shipped.
- Piper peak-normalises each sentence, so voices differ in loudness; E10's prerender should normalise loudness (tech.md §4.3 proposes −16 LUFS).

## Standalone Piper (TECH-4)

- piper1-gpl v1.8.0 (the pinned release) publishes only Python wheels: Linux x86_64 and aarch64, Windows amd64, macOS x86_64 and arm64, about 34 MB each, with espeak-ng compiled in (`espeakbridge`) and its data. They need a Python interpreter; there is no standalone binary.
- The same source tree builds `libpiper` (C API, `libpiper/README.md`) with CMake, which downloads onnxruntime and builds espeak-ng; a standalone CLI would be a small C++ wrapper around it.
- The last standalone binaries are from the archived MIT `rhasspy/piper`, release `2023.11.14-2`: `piper_windows_amd64.zip` (22.5 MB), `piper_macos_x64.tar.gz` and `piper_macos_aarch64.tar.gz` (19.1 MB), `piper_linux_x86_64.tar.gz` (26.5 MB). They link espeak-ng (GPL-3.0), take JSON lines on stdin (`--json-input`) and read the same `.onnx` + `.onnx.json` voices. S7b tests the Windows one under Wine.
